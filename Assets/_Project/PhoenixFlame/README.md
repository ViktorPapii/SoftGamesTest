# Phoenix Flame

A fire burning in the dark, and a button that walks its colour orange → green → blue → orange. Every
pixel of it is generated by the project: the textures are drawn by an editor tool, the particle
systems are assembled by another, and the colour cycle is an AnimatorController with one state per
palette.

Scene: `Assets/_Project/PhoenixFlame/Scenes/PhoenixFlame.unity`. Nothing to start — the fire plays on awake.

## The fire

`Flame.prefab` is five particle layers and a 2D light, drawn back to front:

| Layer | Material | What it does |
|---|---|---|
| `Smoke` | `Smoke_Alpha` | Alpha blended, drifts off the top and grows. The only layer that is not additive. |
| `Glow` | `Glow_Additive` | A few huge, faint billboards pooling at the base. |
| `Body` | `Flame_Additive` | The bulk of the flame: tongues rising, shrinking to nothing. |
| `Core` | `Flame_Additive` | Smaller, shorter lived, inside the body. This is what keeps the base white hot. |
| `Embers` | `Ember_Additive` | Sparks lifting away, winking through an uneven alpha curve. |
| `Light` (Light2D) | — | What the fire throws on the backdrop. Flickers on Perlin noise. |

All four materials live in `Assets/_Project/PhoenixFlame/Art/Materials`. `Flame_Additive` and `Smoke_Alpha` draw
3×3 flipbooks — played once across each particle's life from a random start frame, which is where the
fire gets its detail; the noise module only has to nudge the plume.

Every layer starts at zero speed and climbs on `velocityOverLifetime` plus a buoyancy force, so
particles accelerate as they rise the way hot gas does; `limitVelocityOverLifetime` on the body is
where the plume stops accelerating and spreads instead. Shape is a thin slab at the base, not a
point, so the fire has a width to grow out of.

Around 180 particles are alive at once, all on one draw call per layer.

## Colour

`FlamePalette` is five colours — core, body, ember, smoke, glow. `FlameView.ApplyPalette` writes them
into each layer's start colour and into the light; shape, timing and the alpha envelopes stay on the
prefab, so a palette change repaints the fire without touching how it moves. Nothing allocates: the
particle modules are structs that write straight through.

The split is: **the controller graph owns the cycle, the asset owns the colours.**

`FlameColor.controller` has one state per colour, named after it, chained on a `Next` trigger:

```
Orange ──Next──▶ Green ──Next──▶ Blue ──Next──▶ Orange
```

Every state plays the same clip, `Flame_Fade`, which keys a single float from 0 to 1 on an ease over
1.25 seconds, and carries a `FlameColorState` behaviour that names the state to the controller as it
is entered. So the colour being entered comes from the graph, the fade shape comes from the clip, and
`FlameColorController` only mixes:

```
press ──▶ SetTrigger("Next") ──▶ state entered ──▶ leaving = mix on screen, target = state's palette
                                 clip restarts  ──▶ fade: 0 ─ease─▶ 1
                                                    fire = Lerp(leaving, target, fade)
```

Because the colour being left is snapshotted from what is on screen, a press mid-fade carries on from
the mix that is burning rather than snapping back. `OnDidApplyAnimationProperties` fires once the clip
has written the frame's `fade`, and that is where the mixed palette reaches the particles. Nothing
polls; there is no `Update`.

**The transitions are 0-length, and have to stay that way.** Every state plays the same clip, so a
blend would mix the outgoing `fade` — sitting at 1 — into the incoming one and start the fade
part-way through. The smoothness is the clip's job.

The colours live in `Assets/_Project/PhoenixFlame/ScriptableObjects/FlamePalettes.asset` — a named list edited in the
inspector, and editable while the game runs. **No colour is inside an animation**, so retuning orange
is one colour picker and no re-keying. The link between the two is the name: a state matches the
palette entry it is named after, and a mismatch logs an error rather than leaving the fire stuck. A
fourth colour therefore means an entry *and* a state.

The button calls `FlameColorController.Next()` through its `UnityEvent`, and the readout in the
corner is the palette's own name, tinted with its body colour.

## Art assets

`Art/Images/ember_dot.png`, `flame_glow.png` and `backdrop.png` are white with the shape in the alpha
channel, so one texture serves every colour in the cycle — colour arrives per particle.

`Prefabs/Flame.prefab` is an ordinary asset, edited in the inspector.

`Animation/FlameColor.controller` and `Flame_Fade.anim` are generated from the palette asset by
**Tools ▸ SoftGames ▸ Phoenix Flame ▸ Rebuild Colour Animator**. Adding a colour is therefore one
entry in the palette asset and one run of that tool — it builds a state per entry, named after it,
chained on the `Next` trigger. The palette asset is only read; the tool never writes colours.

The link between the two is the name, and `FlamePaletteGraphTests` is what keeps them honest if the
tool is not run.

## Rendering

`Flame_Additive` and `Smoke_Alpha` are on built-in `Mobile/Particles/Additive` and
`Mobile/Particles/Alpha Blended`, which multiply the texture by the particle's colour — which is what
lets the palette tint art it did not author. The glow and the embers use `SoftGames/Flame Particle`
(`Assets/_Project/PhoenixFlame/Art/Shaders/FlameParticle.shader`), a small unlit shader whose output is premultiplied by alpha
so one fragment path serves both blend modes. Its pass carries no `LightMode` tag, which is what puts
it in the 2D renderer's unlit queue.

Colours stay inside 0–1, and **there is no post-processing** — no volume, no bloom, no HDR buffer on
the camera. The flame art has soft light baked in and the `Glow` layer is a wide additive billboard,
so the halo is painted rather than filtered; the `Glow` layer and the core's alpha carry the heat.
That keeps a full-screen post chain, a half-float colour target and the blit off a WebGL build,
which is where those cost most.

The backdrop is a lit sprite, so the flame's `Light2D` plays across it and the whole scene shifts hue
with the fire.

## Layout

The camera is orthographic at a fixed size, so the visible world height never changes and the fire is
the same size on every device; only the width grows with the aspect. The UI is a scaling overlay
canvas with each element in its own corner — frame rate top left, title top centre, the colour button
bottom left and the colour readout bottom right — which holds up from ultrawide to portrait phone
without a second layout, and leaves the middle of the screen to the fire.

## Frame rate readout

`SoftGames.Core.FpsCounter` rides on the persistent GameManager and is drawn with IMGUI, so it is
present in this scene without the scene owning anything.

## Tests

- `FlamePaletteGraphTests` (edit mode) — the palette asset and the animator graph are joined by
  state name alone, so renaming an entry compiles, imports and plays, and only turns into a red
  console the moment that colour comes round. This asserts the two name sets match in both
  directions, and that palette names are distinct.
- `PhoenixFlameSceneTests` (play mode) — loads the scene, presses the colour button and asserts the
  fire's colour moved, without naming which colours: the palettes are an asset anyone may retune. It
  names no Phoenix Flame type either, driving the button and reading the particle system, so it
  covers the whole chain and fails on any error the scene logs.
